FocusFleet

Real-time driver fatigue monitoring for fleet-style demos: a webcam feed runs through computer vision, surfaces clear active → warning → drowsy states, and logs sessions for drivers and admins—not a one-off script, but a full web product.

Python, FastAPI, Next.js, MediaPipe Face Mesh, OpenCV, optional Keras, SQLite, Docker · GitHub · live demo

Problem

Drowsiness shows up in the face before it shows up in telematics. A useful system has to react on live video, explain itself on screen, and avoid crying wolf—one blink should not trigger a fleet alert.

I also wanted something you could hand to a recruiter or teammate cold: register, open monitoring, see annotated frames and status, and (for admins) skim session history. That meant growing past a desktop or Gradio prototype into a static Next.js UI, a FastAPI backend, and one shared focusfleet/ detection package used everywhere.

From Gradio to Next.js

The project started as a CustomTkinter desktop app and a Gradio Space—fast for tuning MediaPipe thresholds and trying the Keras classifier on uploads. The product path today is different: Next.js for login, dashboard, live monitoring, analytics, and admin; FastAPI for auth, sessions, and analytics; the same CV core behind both.

Production ships as one Docker container (Hugging Face Space on port 7860): Uvicorn serves the exported Next build and the API on the same origin. Locally, Next dev on port 3000 proxies REST to FastAPI on 8000. Optional web/main.py Gradio entry remains for CV-only experiments without the full stack.

In the browser

What the model stack is

MediaPipe Face Mesh finds facial landmarks on each frame. Eye aspect ratio (EAR) and mouth opening catch low lids and yawns; drivers can tune the EAR threshold in the UI. An optional Keras file (driver_drowsiness_model.keras) loads when present—face crops resized to 224×224—for a secondary CNN check (including static image classification). The legacy desktop README describes a MobileNetV2-style classifier as validation on top of geometry; the current monorepo README documents the artifact and pipeline, not a training notebook, dataset splits, or held-out accuracy.

Debouncing and alerts

Per-frame geometry is noisy, so process_frame feeds a small state machine: sustained low EAR or yawn promotes warning, then drowsy only after about two seconds of continuous signal; losing the face is tracked separately. Alert audio fires only after impairment lasts longer (configurable, default eight seconds), so brief glances do not blast the speaker. Session logs record state transitions instead of every frame.

Live monitoring path

After sign-in, the driver starts a session with REST, then sends JPEG frames on /ws/monitoring/{session_id}. Each frame runs through shared detection; the client gets status JSON and an annotated frame. Stopping the session finalizes log files the dashboard and admin views can read.

Proof

Try it in the browser

The public demo runs on a Hugging Face Docker Space—same codebase as GitHub: register as a driver, open monitoring, and watch states change with your camera. Admins get a fleet-oriented overview and log access after sign-in.

huggingface.co/spaces/ArnavPoswal15/FocusFleet · The repo describes features and architecture; it does not publish a fixed FPS target or test-set accuracy, so this page does not claim those numbers.

What I’d change next

  • Replace placeholder analytics charts with daily aggregates once enough sessions exist in demo data.
  • Benchmark WebSocket round-trip latency on Space hardware and expand negative testing (glasses, low light, profile angles).
  • Publish or link proper training notes for the Keras artifact if the CNN stays in the cascade—today only the weights path and inference code are in-tree.
  • Keep Gradio as a CV sandbox so Next + FastAPI remains the single product surface.
